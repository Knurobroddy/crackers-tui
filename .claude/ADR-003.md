# ADR-003: Code conventions

- Status: Accepted
- Date: 2026-09-27
- Rules: [CONVENTIONS.md](../CONVENTIONS.md). This ADR records why they were chosen.

## Context

At v0.1.0 (ADR-002) the code works and is well tested, but it is hard to read:

- long functions (`packer.Build` 116 lines, `tui.Update` 108, `Engine.Install` 93);
- `if err == nil && …` chains;
- closures inside long functions;
- short ad-hoc names (`pr`, `st`, `j`);
- local constants and anonymous types inside functions;
- user-facing prose built deep in the engine;
- a string-keyed failpoint hook in production code.

The planned profiles feature (a new `app`, `profile` and `activate` layer, then Minecraft) will grow the codebase a lot. The goal is code built from separate blocks that can each be read, replaced and tested on their own.

## Decisions

| Decision | Why |
|---|---|
| Base on the Google Go Style Guide; our doc lists only additions and overrides | Well known and Go-idiomatic; it already settles most naming questions, so our doc stays short and checkable. |
| Short names only for receivers, short loops and universal idioms; a fixed abbreviation list | Google's "length proportional to scope" still allowed the unreadable `pr`/`st`/`j` style in long functions. A fixed rule is easier to apply than a line threshold. |
| No closures except short, API-required ones | Inline logic hid control flow and captured state; named functions give it a name and make it testable. |
| Function limits: 120 lines, cognitive complexity 30, nesting 3, 4 parameters (unless the struct would be single-use) | Loose enough to avoid artificial splitting, strict enough to stop the worst cases. Single-use parameter structs add indirection without clarity. |
| Few comments: doc comments on exported identifiers, "why" comments only | Names should carry meaning; ADR section references in code went stale. |
| Types and constants at package level; `errors.go` per package; minimal error types | Definitions inside functions hid knowledge; one place per package for errors, and reuse keeps callers' `errors.As` checks simple. |
| Technical errors below `app`, one user-message mapper | Advice text was scattered through the engine and duplicated; one mapper keeps it DRY and replaceable per UI. |
| Global `slog` default logger, no injection | This is a desktop tool with one log file and no tests assert on logs. Injecting a logger into every constructor added a parameter everywhere for no benefit. This is the only allowed singleton. |
| Consumer-declared small interfaces, constructor injection, filesystem abstraction in the engine | Lets every block be replaced by a fake. The fs abstraction replaces the failpoint test hook, so tests no longer reach into production flow. |
| DRY: knowledge always, code by rule of three | Knowledge duplicated drifts. Code duplication extracted too early creates wrong abstractions. |
| Tests: stdlib + go-cmp, `TestType_Method_preconditions_results`, fakes not mocks, three layers (unit, functional against a fake world, teatest UI flows) | The Google style guide recommends testing without assertion libraries. Functional tests with real components protect behavior through refactors. |
| golangci-lint blocking in CI from day one | Rules nobody checks decay. The refactor branch turns the gate on in its last commit, so `main` is never red. |

## Consequences

- One refactor branch brings the existing code to these rules, package by package bottom-up, with the functional test safety net written first against current behavior.
- `engine`'s failpoint is replaced by a filesystem interface, and `logx` and the `log` constructor parameters are removed.
- The TUI moves onto a new `app` layer, which the profiles feature later extends.
